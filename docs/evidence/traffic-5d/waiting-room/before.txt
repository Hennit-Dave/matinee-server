READ THIS AS:
  entry. There is no line: joining is a 404, and all 100 users read the seat map and could go on to hold seats at the same moment. RULES D5.3
         asks for the opposite: past a limit, new users queue and are admitted at a fixed rate.
  drain, lapse. Nothing to measure: there is no queue to drain and no pass to lapse.
  burst. All 80 are served. That is not a sign of protection: the server has no in-flight limit at all, so the 801st concurrent request would be
         served too, slower and slower, until something upstream (the database pool, Railway) fails in a way the app shows as a crash or a timeout.
         NOTE: this machine cannot produce a REAL overload, so the after run demonstrates the mechanism with a deliberately small in-flight limit.
