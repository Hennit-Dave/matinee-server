# Handoff: cancelled-showtime refunds, server side (branch `feat/payments-p3`)

Payments slice P3 (brief Req 4 / RULES D4.7). Plan approved by Dave 2026-11-20 with four decisions: (1) an admin-key'd
`POST /admin/showtimes/:id/cancel` endpoint (not an ops script, and not user-reachable — there is no auth yet); (2) HTTP
410 `showtime_cancelled`; (3) hard-delete the booking rows on refund (the order + ledger keep the money truth); (4) the
mobile copy switch is a separate follow-up PR. Also folded in at approval: the processor's catch now handles
`showtime_cancelled` (not just `seat_taken`/`seat_not_held`) to close the TOCTOU window, and the read-side exclusion
(cancelled showtimes drop out of `forMovie` and the seat map returns `null`).

## What changed

- **Data model** (`20261120000000_showtime_cancelled_at`): `showtimes.cancelled_at` (nullable timestamptz) — one primary
  write marks it (`UPDATE … WHERE cancelled_at IS NULL`), presence = cancelled.
- **Admin cancel** `POST /admin/showtimes/:id/cancel` (`src/showtimes/cancel{Repo,Service,Routes}.ts`, `src/http/adminKey.ts`):
  mounted only when `ADMIN_API_KEY` is set, `X-Admin-Key` compared with a constant-time hash compare; wrong/missing key is
  `403 invalid_admin_key`. Marks the showing, then enqueues `showtime.cancelled` (always, so re-cancel is the recovery path).
- **Reject a dead showing**: `BookingService.checkSeats` throws `410 showtime_cancelled`, so holds, checkout and the webhook
  confirm are all refused before any PaymentIntent or seat. `forMovie` drops cancelled showtimes; `seatService.forShowtime`
  returns `null`.
- **Refund job** (`src/payments/cancelRefund.ts`, worker handles `showtime.cancelled`): walks the showtime's orders —
  `succeeded` → Stripe refund (`refund_<pi>`) + `refund` ledger row (`showtime_cancelled_refund`) + order `refunded` +
  delete bookings; `requires_payment` → cancel the PI + release holds + order `failed` (or defer if the PI can't be
  cancelled); `refunded`/`failed` → skip.
- **Cancellation-aware processor**: `handlePaymentSucceeded` now takes `showtime.isCancelled`, checks it before confirming
  (and refunds), and its catch list includes `showtime_cancelled` — every charge ends `succeeded` or `refunded`.
- **Ledger unchanged** (append-only; `stripeEventId` is nullable, dedup stays on `stripe_object_id` — verified against the
  migration). `.env.example` gains `ADMIN_API_KEY` (name only). ADR 0020, `docs/evidence/payments-p3/README.md`.

## Unproven / carry-forwards

1. **The integration test is not run here** (no `TEST_*` throwaway DB/Redis in this environment; the gate skips it). Run
   `npm run test:integration` against a throwaway Postgres 16 + Redis 8, as P1 did.
2. **Real Stripe test mode is not run here** (no keys; the agent never reads `.env`). `docs/evidence/payments-p3/README.md`
   has Dave's exact cancel + DB-proof steps with throwaway keys in `.env.test.local`.
3. **The worker is not exercised against the real Railway Redis** here — the worker entry compiles and the processor/refund
   functions are unit-tested; the deploy slice wires the second Railway service.
