# Handoff: the Stripe payment engine, server side (branch `feat/payments-p1`)

Payments slice P1 (brief Req 4 + the backend standard). Plan approved by Dave 2026-11-18 with four decisions: (1) refund on
BOTH `seat_taken` and `seat_not_held`, distinct ledger reasons, re-hold-if-free deferred to P3; (2) `confirmBooking` gets the
optional `reference` + idempotent replay, kept minimal; (3) table name `orders`; (4) `stripe` + `bullmq` confirmed.

## What changed

- **Data model** (`20261118000000_payments`): `orders` (PaymentIntent ↔ seats ↔ owner ↔ idempotency key, `reference` = the
  booking `reference`), `ledger_entries` (append-only, `amountCents` positive + `kind`, unique `stripe_object_id`), and
  `processed_stripe_events` (event-id dedup). `bookings` is untouched.
- **Checkout** `POST /showtimes/:id/checkout` (`{ seatIds }` + `X-Client-Id` + `Idempotency-Key`): verifies the caller still
  holds every seat (`BookingService.verifyHolds`, the shared "you may pay" gate), prices the order server-side
  (`Σ seats + SERVICE_FEE_CENTS=150`), creates the PaymentIntent (GBP, metadata, namespaced Stripe idempotency) and returns
  the `client_secret`. A repeated key returns the SAME PaymentIntent; a key reused with different seats is `409
  idempotency_mismatch`; Stripe-down is `503 payment_unavailable`.
- **Webhook** `POST /webhooks/stripe` (`express.raw` only): verifies the signature, records the event id first (dedup),
  enqueues `payment_intent.succeeded`, returns 200 fast.
- **Worker** (`src/jobs/worker.ts`, `npm run worker`, a separate always-on process on Railway Redis): for a succeeded payment,
  records the charge (the money has moved), calls the existing `confirmBooking` with the order's reference, and — if the hold
  lapsed — refunds the PaymentIntent and records the refund. 5 attempts, exponential backoff, then BullMQ's failed set.
- **`confirmBooking`** gained the optional `reference` + an idempotent replay (returns the existing booking instead of
  re-inserting), and `verifyHolds`. The direct `POST /bookings` route is unchanged (still generates its own reference, still
  the k6 load-test path).
- **Never cached:** payment status and webhook idempotency records are Postgres-only (RULES C4). Redis is only the queue.
- New error codes `idempotency_mismatch` (409) and `payment_unavailable` (503); a `checkout` rate-limit policy (5/20); logger
  fields `reference`/`paymentIntentId`/`eventId`/`jobId`/`amountCents`/`eventType`; `.env.example` gains
  `STRIPE_SECRET_KEY`/`STRIPE_WEBHOOK_SECRET` (names only, values never logged).
- **Docs:** ADR 0019, README "Payments" section, `docs/evidence/payments-p1/`.

## What passed

- `npm run typecheck`, `npm run lint`: clean. Unit: **361 tests, 266 pass, 0 fail, 95 skipped** (main was 340/248/92; +21 —
  18 payments unit + 3 gated integration). Integration on a throwaway Postgres 16 + Redis 8: **96 of 96** (93 before, 3 new).
  `gitleaks` (history): no leaks.
- **The reconciliation is proven end to end** (`payments.integration.test.ts`): hold → checkout → webhook → worker confirms the
  booking and records the charge; the hold-lapsed case refunds (`charge` + `refund` rows, order `refunded`, zero bookings); the
  event-id dedup enqueues once.
- **The Stripe signature is proven against the real SDK** (`stripe.test.ts`): a genuine signature is accepted, a tampered body
  and a wrong secret are rejected — no fake for that seam.

## Decisions worth knowing (all in ADR 0019)

- **Two idempotency mechanisms, both built:** the checkout `Idempotency-Key` (same PaymentIntent, no second charge) and the
  webhook event-id dedup (skip re-delivered events). They guard different retries.
- **Record the charge first, then confirm.** The money has moved the moment Stripe says "succeeded", so the charge is a ledger
  fact whether the booking lands or the hold refunds.
- **Retry-safe worker:** the three guards (order status, ledger `stripe_object_id`, `confirmBooking`'s reference replay) make a
  BullMQ retry at any point converge — never double-charge, double-book or double-refund.

## Unproven / carry-forwards

1. **Real Stripe test mode is not run here** (no keys; the agent never reads `.env`). `docs/evidence/payments-p1/README.md` has
   Dave's exact Stripe-CLI + test-card steps with throwaway keys in `.env.test.local`. Run it and save the row dumps.
2. **The BullMQ Worker is not exercised against the real Railway Redis** here (only the throwaway local Redis). The worker entry
   compiles and the processor is tested; the deploy slice wires the second always-on Railway service and points it at Railway Redis.
3. **`payment_intent.payment_failed`** is a no-op in P1 (the hold lapses on its own); explicit release-on-failure is P3 polish.
