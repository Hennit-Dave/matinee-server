  and `windowMs` stay. The limiter still runs its Redis script on every request (so 5e measures its cost, not a bypass). The
  named test (`policies.test.ts`) pins "lifts address, not install". This completes the profile switch — it now turns off the
  room, the shedding, the address hold cap AND the address rate limits, from one setting.

  `waiting-room.js` (500 users against a room of 5), `prepare.ts` (seeds the real schema with a fake movie id and writes the

- **Docs.** `docs/TRAFFIC.md` and `docs/SHARDING.md`, plus `docs/evidence/traffic-5e/` (before/after, waiting room, summaries,

- **No migration, no dependency, no service, no secret.** One tiny code change, everything else scripts + docs.

## What passed

- `npm run typecheck`, `npm run lint`: clean. Unit: **340 tests, 248 pass, 0 fail, 92 skipped** (main was 336/244/92; +4).
- **The headline (the graded bit), on the real server over a throwaway stack:**
  - 500 VUs, 10 per seat, hold → confirm: **`hold_201` 50, `hold_409_seat_taken` 450, `booking_201` 50, `unexpected` 0.**
  - `POST /holds` p50 1.15 ms / p99 23.84 ms; `POST /bookings` p50 4.22 ms / p99 22.88 ms.
  - **DB proof:** `COUNT(*)`=50, `COUNT(DISTINCT seat_id)`=50, `GROUP BY … HAVING COUNT(*) > 1` = **0 rows**, 50 distinct owners.
  - **Log proof:** 50 `hold_acquired`, 450 `hold_rejected` (all `seat_taken`), 50 `booking_confirmed`, 0 `booking_rejected`,
    0 `server_busy` / `redis_unavailable` / `rate_limit_unavailable`. Statuses: 100 × 201, 450 × 409, no 500, no 429.
- **The waiting room:** 5 admitted, 495 queued, `ahead_sum` = 122265 (distinct positions 0..494), 7 later admissions spread
  3.0–39.1 s (fixed rate), 0 unexpected across 7,386 requests.
- **The baseline is honest:** before the scaling change the same run was refused 467 × `429 rate_limited` (only 20 bookings),
  captured as `before.txt` — the gap ADR 0016 handed to 5e, now closed.

## A finding worth telling Dave about (the Q8 surprise)

The thing I expected to bite — the 5-connection primary pool — did **not**: 50 concurrent confirms at p99 22.9 ms. What bit was
the **environment**: macOS's 128-slot TCP listen backlog (`kern.ipc.somaxconn`) reset ~370 of 500 connections on an instant
start, before any request reached the app. The scripts use a 0–1 s stagger (still "the same moment" for a 10-minute hold). It is
in `REPORT.md` §6. **Ask Dave interview question 8** ("What did the load test reveal that you did not expect?") and give an
honest verdict, not a pass.

## Unproven / carry-forwards (do not lose these)

1. **`MAX_IN_FLIGHT=250` is still chosen, not measured.** The profile turns shedding off so the burst isn't refused; the server
   absorbed 500 concurrent holds + 50 bookings at p99 24 ms, so 250 is conservative. Set a real figure with a ramp test
   (shedding on) in the deploy slice.
2. **Railway re-run.** These scripts re-run against the deployed server (change `BASE_URL`). Also still open from 5c/5d:
   `verify-client-ip.sh` against the real edge, and a real `WAITING_ROOM_MAX_ACTIVE`.
3. **`PRIMARY_POOL_MAX=5`** is adequate at this scale (measured), but only for one showtime's burst; revisit at real
   multi-room concurrency.
4. **Railway's Redis version** is still assumed (CI runs Redis 7, local was 8; the Lua uses basic commands only).
